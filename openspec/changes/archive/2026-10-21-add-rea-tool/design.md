# Design

## Context

See `proposal.md` — Why. The `ai` module is a three-layer plugin (`config/` → variables, `internal/` → implementation, `pkg/` → public wrappers) whose tools are registered at four fixed points (`config/base.zsh`, `internal/main.zsh`, `pkg/main.zsh`, `internal/tools.zsh`). Two neighbours define the patterns this change follows: `tuicr` for a PATH-only binary (config/internal/pkg trio, load guard, curl installer) and `freellmapi` for the four-point registration and message discipline.

Constraints that shape the approach:

- Upstream REA 6.7.0 supports only Node `^22.19.0 || ^24.11.0 || >=26.0.0` — 23.x and 25.x are explicitly unsupported — and its installer never edits shell rc files, so PATH handling is entirely ours.
- `core::exists` wraps `command -v` and caches only positive results (`system/core/internal/api.zsh`); it cannot express "installed but not yet on PATH".
- `message_error` returns 0, so every failure branch must `return 1` explicitly.
- `zsh/modules/ai/` is sourced by the module loader before the `docker` module, and the `ai` module must stay usable on machines without Node.
- `README.md` / `README.yaml` have no per-tool slot; they are generated by `task readme` and are out of scope.

## Goals / Non-Goals

**Goals:**

- A REA install path that is safe to run repeatedly, fails loudly when Node is incompatible, and never blocks the rest of the module from loading.
- A load step that makes `rea` available on the first shell after a `~/.local/bin` install, without duplicating `PATH` entries on re-source.
- Agent-side availability: the OpenCode config template carries a version-pinned `mcp.rea` entry; post-install guidance documents the 172 MCP tools and the six MCP prompts.

**Non-Goals:**

- No custom skill sync: skill installation/refresh is delegated to `rea setup` (binding user decision).
- No MCP server implementation in zsh: REA's MCP server is upstream, launched via `npx`.
- No `data/rea/` templates, no README regeneration, no new lifecycle verb, no changes to `tool-lifecycle-standardization`.
- No Node version manager integration (`mise`/`asdf`/`nvm`): the gate reports incompatibility, it does not install Node.

## Decisions

### D1 — Three layers, mirrors of the `tuicr`/`freellmapi` shape

`config/rea.zsh` holds only exported `ZSH_AI_REA_*` values; `internal/rea.zsh` holds all logic (`ai::internal::rea::*`); `pkg/rea.zsh` holds one-line delegates (`ai::rea::*`). Rationale: matches the module's existing convention and `ai-config-per-tool`, so tool variables never leak into `config/base.zsh`. Alternative (single `internal/rea.zsh` doing everything) rejected: it breaks the config/registry split every other tool follows.

### D2 — Load guard keys on file existence, not on `core::exists`

```zsh
function ai::internal::rea::load {
    [[ -e "${ZSH_AI_REA_BIN_PATH}/rea" ]] || return 0
    case ":${PATH}:" in
        *":${ZSH_AI_REA_BIN_PATH}:"*) ;;
        *) export PATH="${ZSH_AI_REA_BIN_PATH}:${PATH}" ;;
    esac
}
```

Rationale: the curl installer drops the binary into `~/.local/bin`, which is not necessarily on `PATH`; `core::exists rea` would only succeed once the directory is already on `PATH`, so the first shell after install would still not find `rea`. tuicr's `core::exists tuicr` guard assumes a pre-existing `PATH` entry; REA cannot. The `case` membership check makes re-sourcing the plugin idempotent (no unbounded `PATH` growth). `return 0` on absence keeps the module loadable on machines without REA.

### D3 — Node gate as a pure, testable helper

`ai::internal::rea::node_version_supported <version>` accepts an explicit string (e.g. `v24.11.0`) and returns 0/1; `ai::internal::rea::node_check` feeds it `node -v` and emits the error. Parsing avoids `jq` and any semver dependency:

```zsh
local v="${1#v}" major="${1#v}" rest minor
major="${major%%.*}"
rest="${v#*.}"
minor="${rest%%.*}"
(( major == 22 && minor >= 19 )) || (( major == 24 && minor >= 11 )) || (( major >= 26 ))
```

This matches the engines range exactly: 22.19+ passes, 22.18 fails, 24.11+ passes, 24.10 fails, 23 and 25 fail (no branch matches), 26+ passes. Keeping the comparison in a helper with an argument makes the matrix unit-testable without switching the machine's Node.

### D4 — Install: method selection, idempotency, prerequisites

Order: (1) `core::exists rea` → `message_info "already installed"` + `return 0`; (2) `ai::internal::rea::node_check`; (3) dispatch on `ZSH_AI_REA_INSTALL_METHOD` (`npm` default, `bun`, `curl`), each checking its own tool (`npm`, `bun`, `curl`) via `core::exists` and emitting `message_error` + explicit `return 1` when missing; (4) run the installer; (5) for the curl/npm global layout make `${ZSH_AI_REA_BIN_PATH}` effective; (6) verify that `rea` actually resolves; (7) `message_success` then `post_install`.

Commands:

- npm: `npm install --global "${ZSH_AI_REA_PACKAGE_SPEC}"` (`rea-agents@6.7.0`)
- bun: `bun add --global "${ZSH_AI_REA_PACKAGE_SPEC}"`
- curl: `curl -fsSL "${ZSH_AI_REA_INSTALL_URL}" | bash -s -- --version "${ZSH_AI_REA_VERSION}" --no-setup` — the upstream installer defaults to `npm install --global --prefix "$HOME/.local"` on Linux, hence `${ZSH_AI_REA_BIN_PATH}=${HOME}/.local/bin`.

Rationale for a configurable method: Linux CI/containers often lack bun while curl is universal; npm matches upstream's documented path. Alternatives rejected: always-curl (ignores a user's existing npm-managed install and its global prefix), `npx`-only (re-downloads 172-tool package on every agent start, and `rea doctor`/`rea setup` would be unavailable), vendoring `install.sh` (upstream drift).

**npm global-prefix preflight (fallback to the upstream installer).** The npm branch probes `npm prefix --global` before installing. When that prefix is not writable — the Nix case: the global prefix is a read-only `/nix/store/...` path, so `npm install --global` fails with ENOENT/EACCES and the module's own primary host cannot use the default method — the function emits a `message_warning` naming the unwritable prefix and the `ZSH_AI_REA_INSTALL_METHOD` override, and falls back to the upstream curl installer for that run (same prerequisites, same failure handling, shared `ai::internal::rea::install_via_curl` helper). The default method stays `npm` (task 1.1): only the unwritable-prefix case diverts, so a normal Node installation keeps the documented path.

**Non-interactive installer.** The curl invocation passes `--no-setup`: upstream `install.sh` otherwise launches the interactive setup wizard (including the Hopper prompt) on a TTY, which would block a batch `ai::install` mid-run. Setup ownership stays with `ai::rea::setup` (D5).

**Post-install reachability check.** A zero exit from the installer does not mean `rea` is usable: npm installs into `$(npm prefix --global)/bin`, bun into `$(bun pm bin -g)`, and only the curl installer writes to `${ZSH_AI_REA_BIN_PATH}` — none of the first two is guaranteed to be on `PATH`, and none of them equals `${ZSH_AI_REA_BIN_PATH}`. After the load guard, the function checks `core::exists rea`; when it fails it emits a `message_warning` naming the directory the selected method actually installed into, tells the user to add that directory to `PATH` or run `ai::rea::doctor`, and returns 1 — an unreachable binary is an incomplete install, not a success, and claiming success would cause a silent reinstall on the next run. Only a resolvable `rea` reaches `message_success` + `post_install`, which reports the real `command -v rea` location instead of only the configured `${ZSH_AI_REA_BIN_PATH}`.

### D5 — Setup delegates the skill, non-interactive by default

`ai::internal::rea::setup` runs `rea setup` when stdin is a TTY (guided flow registers MCP and installs the skill), and `rea setup --yes --skill` otherwise (skill only, no client-specific MCP writes from a background/batch context). `ai::rea::setup` is added to the `ai::setup` aggregate with the same `|| (( failures++ ))` pattern used for codegraph/openspec.

Rationale: upstream owns the skill destination rules (`~/.agents/skills` only when no client is selected, symlinks refused) and the client-specific MCP formats; duplicating them would drift. Alternative (own `~/.agents/skills/reverse-engineer-anything` copy step) rejected — it would bypass upstream's symlink and client-selection rules, and `rea doctor --skill --json` would no longer validate our copy.

### D6 — MCP registration: version-pinned template entry, `npx` launcher

Add to the OpenCode template `zsh/modules/ai/data/opencode/opencode.jsonc` inside the existing `mcp` table:

```jsonc
"rea": {
  "enabled": true,
  "type": "local",
  "command": ["npx", "-y", "rea-agents@6.7.0", "mcp"]
}
```

The entry is placed among the mcp servers (grouped with the other local stdio servers) and reaches the active config through the existing `ai::opencode::sync` rsync step, which is already part of `ai::sync`. Pinning 6.7.0 is deliberate: `rea setup` pins persistent registrations to the version that ran setup, and `@latest` in a durable config makes agent startups depend on the registry's current tag. `npx` mirrors the canonical upstream `mcpServers.rea` snippet and honours `OPENCODE_CONFIG_DIR`/`OPENCODE_CONFIG` through OpenCode itself. Alternative (`rea mcp` assuming the binary is on PATH) rejected: the agent process may start before any shell sourced our load guard.

### D7 — Documentation over duplication for the agent surface

Post-install guidance (message_* only) names the MCP server, the analysis tool surface, the six prompts, and `rea doctor --json` for verification. Rationale: the tool count is version-specific (172 at the main commit) and the prompt list is stable, so the prompts are enumerated and the tool count is described rather than hard-coded into dispatch. Alternative (zsh wrappers per MCP tool) rejected: those are agent-side calls, not shell commands.

### D8 — No spec change to `tool-lifecycle-standardization`

`install`, `setup`, `update`, `upgrade` are already permitted verbs; `doctor` and `uninstall` are subcommand wrappers, not lifecycle verbs. `status` is not implemented because `rea doctor` already is the read-only state report and adding `ai::rea::status` would duplicate it. Therefore no existing requirement text changes.

## Risks / Trade-offs

- **Node gate false negatives** (`node -v` with a distro suffix such as `v24.11.0-pre`) → parsing stops at the first dot for major and minor, ignoring prerelease/build suffixes; only major/minor drive the verdict. Mitigation: pure helper is unit-tested against the full allowed/rejected matrix in tasks.
- **Upstream engine range changes** (REA may drop 22 or start supporting 25) → the range lives in one helper with a single comparison line; the `ZSH_AI_REA_PACKAGE_SPEC` pin keeps behavior reproducible until the pin is bumped.
- **Batch install now includes REA** — `ai::install` will attempt it on every machine; a Node-gate failure must not abort other tools → the `case` dispatcher already continues after a per-tool non-zero status; REA install returns 1 without exiting.
- **Version pinning drift** — docs elsewhere may cite `rea-agents@6.4.0`; the pin lives in `config/rea.zsh` and the template, and tasks grep both for `6.7.0` so a stale reference is caught in review.
- **`~/.local/bin` vs npm prefix** — on macOS npm global installs land in `$(npm prefix --global)/bin`, which may differ from `ZSH_AI_REA_BIN_PATH`; on Nix the global prefix is a read-only store path and `npm install --global` cannot write there at all. Mitigated: the npm branch runs a global-prefix preflight and falls back to the upstream curl installer (with a warning naming the prefix and the `ZSH_AI_REA_INSTALL_METHOD` override) when the prefix is not writable, and the post-install reachability check warns with the method's real install directory and returns non-zero when `rea` does not resolve — neither an unwritable prefix nor an unreachable binary is reported as a successful install. The default method stays `npm` for a normal Node installation.
- **Interactive `rea setup` in the aggregate** — `ai::setup` on a TTY will block on prompts. Trade-off accepted (guided registration is the point); the non-TTY branch keeps CI/install scripts unattended.
- **Duplicated PATH probe** — the load guard checks `-e` rather than `command -v`, so a broken symlink is treated as absent; harmless, and consistent with the archify/omp pattern.

## Migration Plan

1. Land the three new files and the five registration edits; existing users see no behavior change until `rea` is installed (load guard is a no-op, install only runs from `ai::install`/`ai::rea::install`).
2. Run `ai::rea::install` on a supported Node runtime; the curl method requires `curl` and writes to `~/.local/bin`; the npm method requires npm.
3. Optionally run `ai::opencode::sync` (or `ai::sync`) to propagate `mcp.rea`, then restart the agent.
4. Rollback: delete the three files, revert the five registration lines and the `mcp.rea` template block, remove `~/.agents/skills/reverse-engineer-anything` and `~/.rea` if a full uninstall is wanted (`rea uninstall --purge-data` handles the latter).
