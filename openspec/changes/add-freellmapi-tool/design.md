# Design

## Context

The `ai` module follows a three-layer per-tool layout (`config/<tool>.zsh` → `internal/<tool>.zsh` → `pkg/<tool>.zsh`) registered at four points: sources in `zsh/modules/ai/config/base.zsh:16-52` plus the `ZSH_AI_TOOLS` registry (`config/base.zsh:55-74`, last entry `omniroute` at line 73), sources in `zsh/modules/ai/internal/main.zsh:5-47` plus the "Load paths" block (`internal/main.zsh:61-76`, only 15 of 18 registry tools have a `::load` invocation), sources in `zsh/modules/ai/pkg/main.zsh:5-47` (no `::load` invocations), and the install dispatch `case` in `zsh/modules/ai/internal/tools.zsh:9-52`.

`freellmapi` breaks the module's core assumption: no binary ever lands in the PATH. Its official installer (`https://freellmapi.co/install.sh`) deploys a Docker Compose service (pinned `ghcr.io/tashfeenahmed/freellmapi:latest`, `.env` with a 64-hex `ENCRYPTION_KEY`, healthcheck `GET /api/ping`, named volume `freellmapi-data`) and installs no executable, no shell hook, no completion. Consequently `core::exists freellmapi` (`zsh/system/core/internal/api.zsh:27-39`) can never return true — and since the cache only stores positives (`api.zsh:33-36`), a guard built on it would re-run the full install (image pull + up + 60s health poll) on every batch install.

There is no Docker precedent inside `ai`: the only daemon-style code is `pkg/hunk.zsh:15` (spawns its own process), and no `core::docker*`/`core::compose*` helper exists anywhere in `zsh/system/core/`. The closest conceptual mold is `omniroute` (`config/omniroute.zsh`, `internal/omniroute.zsh:16-55`, `pkg/omniroute.zsh`): a local service with a port, its own `::install`/`::upgrade`, and thin public wrappers. See proposal.md — Why for motivation.

## Goals / Non-Goals

**Goals:**
- Manage `freellmapi` as a first-class `ai` tool backed by the official Docker Compose deployment, following the three-layer layout, variable prefix (`ZSH_AI_FREELLMAPI_*`), namespace (`ai::internal::freellmapi::*` / `ai::freellmapi::*`), and the four registration points.
- An idempotent lifecycle — `install`, `upgrade`, `status` — whose "installed" detection works without a PATH binary and never re-deploys over an existing `.env`/`ENCRYPTION_KEY`.
- Explicit install dispatch in `internal/tools.zsh` so the batch installer never falls through to the generic package-manager path.
- Post-installation guidance (dashboard URL, provider keys, `/v1` + `/v1/messages`, `ENCRYPTION_KEY` loss warning) and spec deltas for `ai-freellmapi` and `tool-lifecycle-standardization` (`status` verb).

**Non-Goals:**
- The homonymous npm CLI `freellmapi` (npx/bunx agent configurator) — explicit scope exclusion in proposal.md.
- Writing or syncing `data/freellmapi/` (the `ai` module does not use the gomplate `render` pattern — it exists only in `zsh/modules/notify/`) and touching `README.yaml` (module-level metadata with no per-tool slots; its README.md is generated by gomplate via `Taskfile.yml`).
- Modifying the `docker` module, adding shared `core::docker*` helpers, or auto-starting the daemon at shell load.
- Managing provider keys or the service `.env` after deployment — the installer is the single writer.
- PATH manipulation, completions, or shell hooks of any kind.

## Decisions

- **Run the official installer (`curl -fsSL "${ZSH_AI_FREELLMAPI_INSTALL_URL}" | bash`) instead of composing the service files by hand.** The installer owns the whole deployment contract — `.env` with a fresh `ENCRYPTION_KEY`, pinned image, healthcheck, named volume, `restart: unless-stopped`, health polling — and is idempotent by design (preserves existing `.env`/`ENCRYPTION_KEY`), which is exactly the guarantee `upgrade` needs. Hand-authoring `docker-compose.yml` would duplicate upstream logic, drift on every upstream release, and risk writing a second, conflicting `ENCRYPTION_KEY` (losing it makes all stored provider keys unrecoverable). What is traded away: fine-grained control over the compose file (extra labels, custom networks, image pinning by digest). Accepted because the module's job is lifecycle management, not service authorship — and re-running the installer *is* the upstream update path. Precedent: every other `curl | sh` tool in the module (`internal/omp.zsh:17`, `internal/tuicr.zsh:24`, `internal/jcode.zsh:17`).

- **Installed guard = on-disk artifacts (`${ZSH_AI_FREELLMAPI_DIR}/docker-compose.yml`), never `core::exists freellmapi`.** `core::exists` probes `command -v` and caches only positives (`api.zsh:33-36`); with no binary it always misses, so the guard would never latch and `install` would redeploy on every invocation. Rejected alternative: caching a sentinel via a shell global — invisible to other sessions, lost on restart, and easy to desync from the actual directory. Rejected alternative: probing the health endpoint as the *guard* — a stopped-but-installed service would look "not installed" and trigger a re-deploy over a live `.env`; endpoint probing belongs to `status` only (see below).

- **`::load` is an explicit no-op.** freellmapi ships no binary, so there is nothing to prepend to `PATH`; the consumer-facing surface is an HTTP endpoint consumed by other tools' config, not a command. It still participates in the "Load paths" block of `internal/main.zsh` so the registration is uniform and the intent (PATH-neutral, succeeds even when `${ZSH_AI_FREELLMAPI_DIR}` does not exist) is documented in code, per the `ai-freellmapi` spec. Rejected: omitting the registration — it would leave 16/18-style inconsistency and hide that the no-op is deliberate. Rejected: exporting a URL/base-path variable from `load` — env exports belong in `config/freellmapi.zsh`, not in the load phase.

- **Explicit `freellmapi)` branch in the `internal/tools.zsh` `case`, before the `*)` fallback.** The fallback is `core::install "${package}"` (`internal/tools.zsh:49-51`), a package-manager dispatch (`brew`/`paru`) that fails silently for a name that is neither a package nor a binary — this is precisely the existing desync: `omp`, `tuicr`, `omniroute`, `jcode`, `archify` each have their own `::install` but no branch, so the registry entry would hit the fallback. The `ai-config-per-tool` spec already mandates the pattern ("Graphify install dispatch reachable", `openspec/specs/ai-config-per-tool/spec.md:71-74`: every registry entry must dispatch to its own install with no dead branch), and the new `ai-freellmapi` spec codifies it as "MUST NOT fall through to the generic `core::install` fallback". Rejected: fixing the general desync in this change — out of scope; freellmapi simply must not join it.

- **`status` as a new lifecycle verb with a delta to `tool-lifecycle-standardization`.** The spec's allowed set is `init, install, setup, update, upgrade` (`openspec/specs/tool-lifecycle-standardization/spec.md:10,17`), none of which can answer "is the service up?" for a binary-less tool. The delta adds `status` to the naming requirement and a new requirement that service-managed tools derive state from artifacts/health endpoint, never from `core::exists` — matching how `ai-freellmapi` implements it, so the two specs stay consistent.

- **Compose/daemon detection: local, self-contained preflight inside `internal/freellmapi.zsh` — verdict: do NOT consume `DOCKER_COMPOSE_TYPE`/`DOCKER_IS_RUNNING`.** The check mirrors the proven pattern from `zsh/modules/docker/internal/linux.zsh:36-43` (`docker compose version &>/dev/null` → plugin, else `docker-compose --version` → standalone, else error) plus `docker info &>/dev/null` for the daemon. Rejected — reuse the docker module's exports, for three independent reasons: (1) **load order**: modules are sourced alphabetically from the glob at `zsh/zshrc:57` (`ai` before `docker`), so during the `ai` load phase those exports do not exist yet; (2) **the exports are unreliable even at call time**: `DOCKER_COMPOSE_TYPE` is only set inside `docker::internal::container::load` on Linux (`linux.zsh:38,40`), but the provider dispatch is last-source-wins (`zsh/modules/docker/internal/main.zsh:14,37-54`) and the default Linux provider overrides that function with a plain `return 0` (`zsh/modules/docker/internal/adapter/docker.zsh:23-25`) — so under the default config the variable is never exported at all; it is likewise never set on macOS (`internal/osx.zsh` has no detection). `DOCKER_IS_RUNNING` (`internal/base.zsh:101-108`) is a snapshot taken at shell startup and goes stale the moment the daemon stops; (3) there is no `core::docker*`/`core::compose*` API to call — the coupling would be to another module's incidental internals, with no contract. The cost of the local check is ~2 fast `&>/dev/null` probes executed only on explicit `install`/`upgrade`/`status` invocations, never at shell load. Rejected — extracting a shared `core::compose` helper now: correct long-term, but it changes `core` for one consumer; tracked as an open question below.

- **`status` strategy: two gates — artifact presence first, HTTP health probe as primary runtime signal; `docker compose ps` only as a fallback.** Flow: (1) if `${ZSH_AI_FREELLMAPI_DIR}/docker-compose.yml` is absent → "not deployed, run `ai::freellmapi::install`"; (2) `curl --max-time <small>` against `ZSH_AI_FREELLMAPI_HEALTH_URL` (default `http://127.0.0.1:3001/api/ping`) → success reports the service as running/healthy, failure reports "deployed but not responding" and suggests `docker compose ps`/`logs -f`. The health endpoint is the right primary signal because it is the same `GET /api/ping` the upstream healthcheck uses — it validates the actual user-facing question ("can I call this endpoint?") end-to-end, `curl` is already a declared prerequisite (spec: "Install validates prerequisites"), and it is format-stable across compose flavors. Rejected as primary: `docker compose ps` parsing — output formats differ between plugin/standalone and across compose versions; also skipped: `docker inspect` health parsing — requires resolving container names from the compose project and adds a docker dependency for what `curl` answers directly. Fallback retained for the pathological case where `curl` is missing: `docker compose -f ${ZSH_AI_FREELLMAPI_DIR}/docker-compose.yml ps -q` non-empty. Note for implementation: `message_*` pass only their first argument through `printf` (`api.zsh:41-56`, wrappers `zsh/system/core/pkg/base.zsh:34-48`), so composed output (URL + state) must be assembled into one string before the call, and every failure path must `return 1` explicitly — `message_error` itself returns 0 (`api.zsh:45-48`).

- **`ZSH_AI_FREELLMAPI_DIR` is the source of truth; `FREELLMAPI_DIR` is propagated per-invocation as an env prefix on the installer call only** (`curl -fsSL "$URL" | FREELLMAPI_DIR="${ZSH_AI_FREELLMAPI_DIR}" bash`). The installer reads the unprefixed `FREELLMAPI_DIR` (default `~/freellmapi`); the module reads its own namespaced `ZSH_AI_FREELLMAPI_DIR` (default `${HOME}/freellmapi`, mirroring upstream). The env prefix guarantees the directory the installer writes is exactly the directory the guard and `status` inspect — even if the user overrides the module variable — without leaking `FREELLMAPI_DIR` into the user's shell. Rejected: a global `export FREELLMAPI_DIR=...` from `config/freellmapi.zsh` — it would hijack any manually-run official installer or other tooling outside the module's control and exports a non-`ZSH_AI_` variable from the config layer (violating the per-tool naming requirement of `ai-config-per-tool`). Rejected: not passing it and assuming the default — the guard and the deployment would silently diverge the moment the user overrides `ZSH_AI_FREELLMAPI_DIR`. The same prefix is applied when `upgrade` re-runs the installer.

- **`PORT`/`HOST_BIND`: the installer's `.env` stays single-writer; the module documents URLs from config defaults, reconciled by read-back at display time.** `config/freellmapi.zsh` defines `ZSH_AI_FREELLMAPI_PORT` (3001), `ZSH_AI_FREELLMAPI_HOST_BIND` (127.0.0.1), and `ZSH_AI_FREELLMAPI_HEALTH_URL`, mirroring upstream defaults — these feed the dashboard/health URLs printed in post-install guidance when nothing is deployed yet. The module NEVER writes `.env`: writing it would create a second writer racing the installer's idempotency contract and could clobber `ENCRYPTION_KEY` (loss = all provider keys must be re-entered). Because a user may legitimately edit `PORT`/`HOST_BIND` in `.env`, `status` and guidance re-read those keys from `${ZSH_AI_FREELLMAPI_DIR}/.env` when the file exists and prefer the read values over the config defaults for display. Rejected: exporting `PORT`/`HOST_BIND` into the installer's environment to pre-seed `.env` — unverified upstream behavior, and an ambient env export would persist beyond the install call. Rejected: always showing config defaults — the printed URL would be wrong after any user customization. The dashboard URL (`http://<HOST_BIND>:<PORT>`) and the `/v1` / `/v1/messages` endpoints are documented exactly once, in post-install guidance and `status` output.

- **`ZSH_AI_TOOLS` ordering: append `freellmapi` after `omniroute` (end of array) — accepted, with the heavy-batch risk documented.** The batch installer iterates the registry sequentially (`internal/tools.zsh:8`), and freellmapi's branch performs `docker compose pull` of a large image plus `up -d` and up to 60s of health polling. Placing it last means every lighter tool has already installed when the slow/failing step runs — the failure cannot block the rest of the batch. Accepted risk: `ai::install` on a fresh machine becomes noticeably slower and network-bound at its tail, and the loop ignores per-branch exit codes (it unconditionally prints success at `internal/tools.zsh:54`), so a failed freellmapi deploy surfaces only through its own `message_error` output; users verify with `ai::freellmapi::status` afterwards. Rejected: excluding freellmapi from the registry — violates both `ai-config-per-tool`'s dispatch requirement and `ai-freellmapi`'s own registry requirement; rejected: first in the array — a slow pull would delay everything downstream for zero benefit.

- **`post_install`: guidance lives in the internal layer and is emitted by a successful `install`; `pkg` exposes `ai::freellmapi::post_install` as a delegating wrapper; nothing is wired into `ai::post_install`.** The `ai-freellmapi` spec requires guidance after a successful install, and the batch path calls `ai::internal::freellmapi::install` directly — so the guidance call must sit at the end of the internal install to be reached from both the direct wrapper and the batch dispatch. The public wrapper (`ai::freellmapi::post_install` → internal guidance function) follows the `ai::tuicr::post_install` precedent (`pkg/tuicr.zsh:27-30`) and lets users re-print guidance on demand. Rejected: invoking it from `ai::post_install` (`pkg/base.zsh:7-10`) — that is a generic module-level banner, not a per-tool dispatcher; adding freellmapi output there would couple base to one tool and print guidance even when the service was never deployed. Rejected: putting the call only in the `pkg` wrapper — the batch path would skip it entirely. Layering is preserved (internal defines and calls; pkg only wraps — matching `pkg/omniroute.zsh:5-15`).

- **Config surface follows the modern suffix convention.** `ZSH_AI_FREELLMAPI_INSTALL_URL`, `_DIR`, `_PORT`, `_HOST_BIND`, `_HEALTH_URL`, `_IMAGE`, `_PACKAGE_NAME` — the `<TOOL>_INSTALL_URL` suffix form used by `omp`/`tuicr`/`jcode` (`config/omp.zsh:7`, `config/tuicr.zsh:6`, `config/jcode.zsh:8`) rather than the legacy `ZSH_AI_INSTALL_URL_<TOOL>` still carried by 12 older tools. Only `${HOME}` and `${ZSH_AI_PATH}` in expansions; `# shellcheck shell=bash` header; no `DEVOPS_*`/`AI_*`; no `echo` anywhere — all output via `message_*`.

## Risks / Trade-offs

- **`curl | bash` supply chain — the install executes remote code at the pinned official URL** → Mitigation: `curl -fsSL` from the HTTPS official domain only (variable lives in `config/freellmapi.zsh`, no hardcoded URL elsewhere), prerequisites validated before the pipe runs, and the deploy is re-runnable/idempotent so a corrupted first attempt is corrected by re-running.
- **Batch install becomes slow/heavy at the tail (large image pull + ≤60s health poll), and `internal/tools.zsh:54` reports success regardless of per-branch failure** → Mitigation: freellmapi registered last so no other tool is blocked; the artifact guard makes re-runs skip the pull entirely; failures emit `message_error` + `return 1` from the branch (loop behavior is pre-existing and unchanged); `ai::freellmapi::status` is the documented verification step.
- **`message_error` returns 0 (`api.zsh:45-48`), so `if ! ...` pipelines can mask failures** → Mitigation: every failure path in the freellmapi functions performs an explicit `return 1` after the message (pattern already used by `internal/omniroute.zsh:30-32`).
- **Losing `ENCRYPTION_KEY` (deleted `.env` or `down -v` + `rm -rf`) makes all stored provider keys unrecoverable** → Mitigation: post-install guidance and `status` warn about it; the module never writes or regenerates `.env`; the rollback procedure below flags the destructive flags explicitly.
- **Module-default port vs user-edited `.env` (`PORT`/`HOST_BIND` drift) would print a wrong dashboard URL** → Mitigation: display-time read-back from `${ZSH_AI_FREELLMAPI_DIR}/.env` (decision above); config defaults apply only pre-deployment.
- **Docker daemon down or compose missing at install time** → Mitigation: preflight `docker info` + compose plugin/standalone probe with `message_error` and `return 1` before the installer runs (spec: "Install validates prerequisites"); no partial state is left because the installer is never invoked.
- **Upstream installer changes behavior underneath us (URL rot, compose format, health path)** → Mitigation: the module composes no service files of its own, so the only pinned assumptions are the install URL, `GET /api/ping`, and `.env` location — all surfaced as single config variables that can be patched independently.
- **Duplicate compose-detection logic vs the `docker` module** → Mitigation: ~4 lines mirroring a proven pattern (`docker/internal/linux.zsh:36-43`), local and side-effect-free; promoting it to a shared helper is deferred (Open Questions) rather than coupling to another module's unreliable exports.

## Migration Plan

1. **Deploy**: land the three new files (`config/freellmapi.zsh`, `internal/freellmapi.zsh`, `pkg/freellmapi.zsh`) together with the four registration edits (`config/base.zsh` source + registry entry, `internal/main.zsh` source + `::load`, `pkg/main.zsh` source, `internal/tools.zsh` branch) and the two spec deltas. Nothing runs at shell load: `::load` is a no-op and no auto-install guard is added, so the first shell after deploy changes no behavior.
2. **First use**: user runs `ai::freellmapi::install` (or `ai::install` / `ai::install` batch) → preflight → official installer → compose up → health poll → guidance. Verify with `ai::freellmapi::status`.
3. **Rollback (module)**: revert the change commit — removes all three files and the four registration points; the registry entry disappears with `config/base.zsh`, so the batch installer stops referencing the tool.
4. **Rollback (service)**: `docker compose -f "${ZSH_AI_FREELLMAPI_DIR}/docker-compose.yml" stop` is the only option that preserves the containers, the named volume, **and** `.env`/`ENCRYPTION_KEY`. `down` without `-v` removes the containers and the network but keeps the named volume and `.env` intact; `rm -rf "${ZSH_AI_FREELLMAPI_DIR}"` deletes `.env` and therefore destroys `ENCRYPTION_KEY` even though the named volume survives; only `down -v` **combined with** `rm -rf` loses the `freellmapi-data` volume and the key at the same time, i.e. every stored provider key. The module itself ships no uninstall verb by design (uninstall = upstream's `docker compose down -v && rm -rf <dir>`).

## Open Questions

- Should compose/daemon probing be promoted into a shared `core::compose`/`core::docker` helper (consumed by both the `docker` and `ai` modules)? Deferrable without affecting this change's specs, tasks, or the local-check decision above — the local helper is intentionally written so it can be swapped for a shared one later.
