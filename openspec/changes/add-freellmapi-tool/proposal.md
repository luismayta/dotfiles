# Proposal

## Why

The `ai` module has no way to manage a tool that ships as a Docker Compose service with no binary in the PATH: every existing guard (`core::exists`) and install dispatch assumes an executable, so a freellmapi install would re-run on every shell load and never be detected as present.

## What Changes

- Add `freellmapi` — an open-source (MIT, Neu Software LLC) LLM router/proxy that aggregates the free tiers of ~34-51 providers behind a single local OpenAI-compatible endpoint — as a tool of the `ai` module, backed by its official Docker Compose deployment (service image, `.env` with `ENCRYPTION_KEY`, healthcheck, named volume).
- **Out of scope (scope exclusion, not a breaking change):** the homonymous `freellmapi` npm CLI (used via `npx`/`bunx` to configure agents such as Claude Code / Codex) is explicitly excluded. Only the Docker service is in scope.
- Add three new files following the module's three-layer layout: `config/freellmapi.zsh`, `internal/freellmapi.zsh`, `pkg/freellmapi.zsh`.
- Register the tool at the module's four registration points: `config/base.zsh` (source + `ZSH_AI_TOOLS` entry), `internal/main.zsh` (tool file + `::load` invocation), `pkg/main.zsh` (pkg source), and the `case` in `internal/tools.zsh` (explicit install branch).
- Introduce an artifact-based guard (service files on disk / Docker daemon reachable) instead of a binary-existence guard, because no `freellmapi` executable ever lands in the PATH.
- Lifecycle functions `install`, `upgrade`, and `status` under `ai::internal::freellmapi::*` with public wrappers `ai::freellmapi::*`.
- Delta to `tool-lifecycle-standardization`: add `status` to the allowed lifecycle verbs, for tools managed as local services with no binary to query.

## Capabilities

### New Capabilities
- `ai-freellmapi`: The `ai` module SHALL manage freellmapi as a tool backed by a Docker Compose service — its own config with `ZSH_AI_FREELLMAPI_*` vars, an install/upgrade/status lifecycle under the `ai::internal::freellmapi::*` namespace with public `ai::freellmapi::*` wrappers, registration at the module's four points, a guard based on on-disk artifacts rather than a binary, and post-installation guidance.

### Modified Capabilities
- `tool-lifecycle-standardization`: `status` is added to the set of allowed lifecycle verbs, for tools managed as local services where no binary exists to query.

## Impact

- **Code affected:**
  - New: `zsh/modules/ai/config/freellmapi.zsh`, `zsh/modules/ai/internal/freellmapi.zsh`, `zsh/modules/ai/pkg/freellmapi.zsh`
  - Modified: `zsh/modules/ai/config/base.zsh`, `zsh/modules/ai/internal/main.zsh`, `zsh/modules/ai/internal/tools.zsh`, `zsh/modules/ai/pkg/main.zsh`
- **External dependencies:** Docker daemon with the Compose plugin (or legacy `docker-compose` binary), `curl`, `bash`. `openssl` is optional for key generation.
- **Specs touched:** new delta under `ai-freellmapi`; delta to `tool-lifecycle-standardization` (adds `status` as a valid lifecycle verb).
- **Risk:** adding `freellmapi` to `ZSH_AI_TOOLS` means `ai::internal::packages::install` will dispatch to it automatically when the registry is iterated — it must therefore carry an explicit `case` branch and a guard that does not depend on a PATH binary, or the install would re-run on every shell load.
- **Decisions — not applicable:** RD-233 AC#15 asked to document the tool in `zsh/modules/ai/README.yaml`; that file is module-level metadata (no per-tool slots) and its README.md is generated by gomplate, so README.yaml is intentionally left untouched. `openspec/specs/tool-implementation-guide/spec.md` documents the `devops::<tool>::internal::<verb>` / `DEVOPS_<TOOL>_` naming, which belongs to the `devops` module and is referenced here only as a non-applicable counter-example; that spec is not modified. `ai-config-per-tool` requirements are satisfied without changes (its install-dispatch scenario is the precedent that a tool registered in `ZSH_AI_TOOLS` must have a `case` branch in `tools.zsh`, which freellmapi also meets).
